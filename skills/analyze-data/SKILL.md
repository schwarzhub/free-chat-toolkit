# Analyze Data

The one rule that makes this trustworthy: **every number you report comes out of an executed `run_code`
run — never from your head.** If you didn't run it, you don't state it. That single discipline is what
separates analysis from confident-sounding fiction.

## 1. Describe before you model
- Load the data in `run_code` (`pandas.read_csv/read_stata/read_sas/read_parquet`; sandbox has
  numpy/pandas/scipy/matplotlib/sympy — **no statsmodels/R**, so estimators are hand-rolled in numpy/scipy).
- Print, don't assume: shape, dtypes, the codebook/variable meanings (`read_document*` a codebook if
  supplied), missingness per variable, ranges/outliers, and the unit of observation. Surface anything
  surprising to the user before proceeding.

## 2. Clean with a log
- Every transformation is a **logged decision**: recodes, dropped rows (how many, why), missing-data
  handling, outlier rules, variable construction, sample restrictions. Print the N at each step (the
  analysis sample funnel). No silent drops — an unexplained change in N is a bug or a finding.

## 3. State the specification up front (before running it)
- Say, in words, *before* estimating: the estimand, the estimator (OLS / logit / DiD / IV / fixed
  effects / …), the **standard-error choice and why** (classical / robust / clustered — on what, and does
  the clustering match the design?), the controls, and the sample. Getting the SE/clustering wrong is the
  most common quantitative error; make it an explicit, defended choice, not a default.
- Note that without statsmodels you're implementing the estimator (e.g., OLS via `numpy.linalg.lstsq`,
  cluster-robust SEs by hand); **validate your implementation** on a tiny known case before trusting it.

## 4. Estimate — via a run
- Run the specification in `run_code`. Report the coefficient, its SE/CI, and N **as printed by the run**.
  Show the code alongside the result so it's checkable. If the run errors or the numbers look off, debug
  and re-run — do not paper over it with a plausible number.

## 5. Robustness battery (right-size to the design)
Run, don't just list, the relevant checks:
- **Specification**: add/drop controls; alternative functional forms; alternative SE/clustering.
- **Sample**: influential-observation / leave-one-out; subsamples; trimming.
- **Design-specific**: DiD → parallel-trends / event-study pre-period + a placebo on pre-treatment years;
  IV → first-stage strength + over-ID; RDD → bandwidth sensitivity + McCrary density; matching → balance.
- **Inference**: multiple-testing adjustment if many outcomes; a sensitivity/partial-R² or bounding
  argument for unobserved confounding where identification leans on selection-on-observables.
Report which survive and which don't — a result that only holds in one specification is a fragile result,
and saying so is the job.

## Output
- A **results table** (coef, SE/CI, N per column) generated by the run, plus the key figure(s).
- The **cleaning + specification log** so a reader can retrace every choice.
- A **reproducibility block**: seed, package versions, and the self-contained code that produced the table.
- A plain-language read of what the estimate does and doesn't support (mind the design — correlational
  evidence is not a causal claim).

## Guardrails
- **No number without a run.** Coefficients, SEs, Ns, p-values, sample sizes — all come from executed
  code, never narrated. This is the whole point.
- **SE/clustering is a decision, not a default** — state and defend it.
- **The sandbox is bounded** (no network, time/memory caps). Big or restricted data may not fit — say so
  and analyze a documented subset rather than fabricating a full-sample result.
- **Don't launder correlation into causation** — the estimator's assumptions are the claim's ceiling.
